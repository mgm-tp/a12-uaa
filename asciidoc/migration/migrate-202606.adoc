===== uaa-authentication

====== UAAJacksonModule extension point

With Spring Security 7 the Jackson integration now mandates an explicit `SecurityJacksonModule` that registers every polymorphic type appearing in token payloads. UAA exposes `com.mgmtp.a12.uaa.authentication.principal.UAAJacksonModule` as that extension point so applications can decide which custom classes (and optional mixins) must be trusted.

* Extend `UAAJacksonModule`, keep a stable module name/version, and register the bean (for example by annotating it with `@Component`).
* Override `setupModule(...)` when you need to add Jackson mixins for domain classes you cannot annotate directly.
* Override `configurePolymorphicTypeValidator(...)` to call `allowIfSubType(...)` for every custom principal type that might be deserialized. If a type is missing, Jackson will fail with `InvalidTypeIdException` during token parsing.

Example:

[source,java]
----
@Component
public class ExamplePrincipalJacksonModule extends UAAJacksonModule {

    public ExamplePrincipalJacksonModule() {
        super(ExamplePrincipalJacksonModule.class.getName(),
            new Version(1, 0, 0, null, null, null));
    }

    @Override
    public void setupModule(JacksonModule.SetupContext context) {
        context.setMixIn(PrincipalMetadata.class, PrincipalMetadataMixin.class);
    }

    @Override
    public void configurePolymorphicTypeValidator(BasicPolymorphicTypeValidator.Builder builder) {
        builder.allowIfSubType(PrincipalMetadata.class);
    }
}
----

*Required:* Yes, if your application puts custom (non-UAA) principal types or domain classes into token payloads. No, if you only use UAA's built-in principal types.

*Migration:* Manual.

*Result:* Custom principal types are registered with the polymorphic type validator and deserialize correctly under Spring Security 7; token parsing no longer fails with `InvalidTypeIdException`.

===== uaa-rest-client

====== HttpClient

* Replaced `OkHttpClient` with Apache `HttpClient` from `org.apache.hc.client5.http.classic.HttpClient` with default implementation `CloseableHttpClient`
** Default configurations:
*** Using `PoolingHttpClientConnectionManager` as connection manager
*** Most of the timeouts (connection, socket, connection request) are set to 5 minutes instead of infinite as previously with OkHttpClient

* `UAARestClientFactoryBuilder.withHttpClient()` now accepts `HttpClient` instead of `OkHttpClient`

*Required:* Yes, if you call `UAARestClientFactoryBuilder.withHttpClient()` or otherwise supply your own HTTP client. No, if you rely on the default client.

*Migration:* Manual.

*Result:* `withHttpClient()` is passed an Apache `org.apache.hc.client5.http.classic.HttpClient`. With the default client, connection, socket, and connection-request timeouts are now 5 minutes instead of infinite.

====== RestTemplate to RestClient

* `RestTemplate` usage has been replaced with `RestClient` (Spring Framework 7 preferred API)

*Required:* No, this is an internal change unless you extended or injected the UAA `RestTemplate` directly.

*Migration:* Manual, only if you depended on the previous `RestTemplate` usage.

*Result:* UAA performs its REST calls through Spring Framework 7's `RestClient`.

==== Removal of deprecated APIs

All APIs that were previously marked `@Deprecated(forRemoval = true)` or `@Deprecated` in earlier releases have been removed.
The following sections describe each removal and the recommended replacement.

[TIP]
====
*Automatic migration tooling (OpenRewrite):* the `UpgradeUaa_10_0` recipe migrates most of these removals automatically.
Running it is *optional* (a convenience) - the same changes can be applied by hand.

It applies one change category:

* *Renames removed getters/setters/builder methods* to their replacements. Examples:
** `ExternalPrincipalImpl.geteMail()` / `seteMail(..)` / `Builder.withEMail(..)` -> `getEmail()` / `setEmail(..)` / `withEmail(..)`
** `TokenData.getAccessTokenExpiration()` / `setAccessTokenExpiration(..)` -> `getTokenRenewInSeconds()` / `setTokenRenewInSeconds(..)`
** `UAARestClientProperties.getGeneratedTokenExpirationHeaderName()` / setter -> `getGeneratedTokenRenewInSecondsHeaderName()` / setter

*Not covered by the recipe (migrate manually):* `AuthorizationData.getAuthenticationTokenExpiration()` - its replacement `getTokenRenewInSeconds()` has a different type and meaning (`Integer` renew interval vs. the removed `Instant` expiration), so it is not a mechanical rename; `JwtTokenData.withExpirationTime(..)` -> `withExpirationSeconds(..)` (takes seconds, not an `Instant`); removed/changed constructors (`AuthorizationData`, `UAARestClientFactory`); the `CertificateConverter` -> `APIKeyConverter` / `CertificateConverter` split; the `UAAAuthenticationSuccessHandler.TOKEN_EXPIRATION_KEY` constant; JSON/config property renames; and CORS `exposedHeaders`.

===== uaa-rest-client

====== TokenData.accessTokenExpiration removed (deprecated since 8.2.2)

The field `accessTokenExpiration` and its getter/setter (`getAccessTokenExpiration()` / `setAccessTokenExpiration()`) have been removed from `com.mgmtp.a12.uaa.client.rest.auth.internal.data.TokenData`.

*Required:* Yes, if your code calls `getAccessTokenExpiration()` / `setAccessTokenExpiration()`.

*Migration:* Automatic by OpenRewrite (`UpgradeUaa_10_0`, rename category); can also be done manually.

*Result:* Calls use `getTokenRenewInSeconds()` / `setTokenRenewInSeconds()` instead.

====== AuthorizationData.authenticationTokenExpiration removed (deprecated since 8.2.2)

The field `authenticationTokenExpiration` (type `Instant`) and its getter `getAuthenticationTokenExpiration()` have been removed from `com.mgmtp.a12.uaa.client.rest.auth.AuthorizationData`.
The two constructors that accepted an `Instant authenticationTokenExpiration` parameter have also been removed.

Use the constructors that accept `Integer tokenRenewInSeconds` instead:

[source,java]
----
// Before (removed):
new AuthorizationData(token, expiration, tokenType, sessionId);
new AuthorizationData(token, expiration, tokenType, sessionId, uniqueId);

// After:
new AuthorizationData(token, tokenType, sessionId, tokenRenewInSeconds);
new AuthorizationData(token, tokenType, sessionId, uniqueId, tokenRenewInSeconds);
----

*Required:* Yes, if your code constructs `AuthorizationData` with an `Instant` expiration or calls `getAuthenticationTokenExpiration()`.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0` - the replacement has a different type and meaning (`Integer` renew interval vs. the removed `Instant` expiration) and the constructor signatures changed.

*Result:* Construction uses the `Integer tokenRenewInSeconds` constructors and reads the value via `getTokenRenewInSeconds()`.

====== UAARestClientProperties.generatedTokenExpirationHeaderName removed (deprecated since 8.2.2)

The property `generatedTokenExpirationHeaderName` and its getter/setter have been removed from `com.mgmtp.a12.uaa.client.rest.config.properties.UAARestClientProperties`.

*Required:* Yes, if your code reads/writes the property or sets it in configuration files.

*Migration:* Automatic by OpenRewrite (`UpgradeUaa_10_0`) for the getter/setter rename; the configuration-file key rename must be done manually.

*Result:* Code uses `getGeneratedTokenRenewInSecondsHeaderName()` / `setGeneratedTokenRenewInSecondsHeaderName()`, and configuration files use the `generatedTokenRenewInSecondsHeaderName` key.

====== TokenConfiguration.generatedTokenExpirationHeaderName removed (deprecated since 8.2.2)

The field `generatedTokenExpirationHeaderName` and its getter/setter have been removed from `com.mgmtp.a12.uaa.client.rest.config.selfconfiguration.TokenConfiguration`.

*Required:* No, unless you called these methods directly.

*Migration:* Manual, only if you called these methods directly.

*Result:* The self-configuration no longer propagates the expiration header name; no remaining references to the removed accessors.

====== UAARestClientFactory public constructors made private (deprecated since 9.2.0)

The three public constructors of `com.mgmtp.a12.uaa.client.rest.config.UAARestClientFactory` that were deprecated since 9.2.0 have been made private.

Use `UAARestClientFactoryBuilder` to create `UAARestClientFactory` instances:

[source,java]
----
// Before (removed):
new UAARestClientFactory(properties, interceptors, errorHandlers, converters);

// After:
UAARestClientFactoryBuilder.create()
    .withProperties(properties)
    .withInterceptors(interceptors)
    .withErrorHandlers(errorHandlers)
    .withMessageConverters(converters)
    .build();
----

*Required:* Yes, if your code instantiates `UAARestClientFactory` via its constructors.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0` (constructor-to-builder rewrite).

*Result:* Instances are created through `UAARestClientFactoryBuilder`.

===== uaa-authentication

`CertificateConverter` has been replaced with two dedicated APIs for API key and certificate authentication.

In previous versions, `CertificateConverter` handled both `APIKey` and `Certificate` authentication types.
This could cause bean conflicts when both authentication mechanisms were configured at the same time.

Starting with this release, the following converters must be used instead:

- `APIKeyConverter` for `APIKey` authentication
- `CertificateConverter` for `Certificate` authentication

This change eliminates bean conflicts and clarifies the separation of concerns between the two authentication types.

*Required:* Yes, if you used `CertificateConverter` for `APIKey` authentication.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0` (converter split).

*Result:* `APIKey` authentication uses `APIKeyConverter` and `Certificate` authentication uses `CertificateConverter`, with no bean conflicts when both are configured.

====== UAAAuthenticationSuccessHandler.TOKEN_EXPIRATION_KEY removed (deprecated since 8.2.2)

The constant `TOKEN_EXPIRATION_KEY` (`"access_token_expiration"`) has been removed from `UAAAuthenticationSuccessHandler`.
The login response, SAML token exchange, and `/token` endpoint no longer include the `access_token_expiration` header or response body field.

*Required:* Yes, if your code references `TOKEN_EXPIRATION_KEY` or reads the `access_token_expiration` header/field.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0`.

*Result:* Token-renewal timing is read from the `token_renew_in_seconds` header/field (constant `TOKEN_RENEW_IN_SECONDS`), which gives the number of seconds after which the token should be renewed.

====== TokenConfiguration.generatedTokenExpirationHeaderName removed (deprecated since 8.2.2)

The field, getter/setter, and builder method `withGeneratedTokenExpirationHeaderName()` have been removed from `com.mgmtp.a12.uaa.authentication.config.client.TokenConfiguration`.

*Required:* Yes, if your `TokenConfiguration.Builder` chains call `withGeneratedTokenExpirationHeaderName()`.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0`.

*Result:* Calls to `withGeneratedTokenExpirationHeaderName()` are removed; token renewal is controlled exclusively via `token_renew_in_seconds`.

====== CORS exposed headers updated

The default CORS exposed headers no longer include `access_token_expiration`.

*Required:* Yes, if your client-side code reads the `access_token_expiration` header or you explicitly configured `exposedHeaders` to include it.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0`.

*Result:* Client code reads `token_renew_in_seconds`, and any explicit `exposedHeaders` configuration no longer lists `access_token_expiration`.

====== JwtTokenData.loginTime and JwtTokenData.expirationTime removed (deprecated since 8.2.2)

The fields `expirationTime` and the builder methods  `withExpirationTime()` have been removed from `com.mgmtp.a12.uaa.authentication.jwt.JwtTokenData`.

*Required:* Yes, if your code calls `withExpirationTime()`.

*Migration:* Manual. Not covered by `UpgradeUaa_10_0` - `withExpirationSeconds(..)` takes seconds, not an `Instant`, so it is not a mechanical rename.

*Result:* `withExpirationTime(instant)` is replaced with `withExpirationSeconds(seconds)`. The computed method `getExpirationTime()` (which returns `issuedTime + expirationSeconds`) is still available.

===== SessionStorageKeys.ACCESS_TOKEN_EXPIRATION and SessionStorageKeys.TOKEN_RENEW_IN_SECONDS removed

The enum members `ACCESS_TOKEN_EXPIRATION` (`"access_token_expiration"`) and `TOKEN_RENEW_IN_SECONDS` (`"token_renew_in_seconds"`) have been removed from `SessionStorageKeys`. These values are no longer stored in session storage.

*Required:* Yes, if your code references `SessionStorageKeys.ACCESS_TOKEN_EXPIRATION` / `SessionStorageKeys.TOKEN_RENEW_IN_SECONDS`, or shares `"access_token_expiration"` via `UaaSecureStorage`.

*Migration:* Manual.

*Result:* References to the removed members are removed; token-renewal timing uses `SessionStorageKeys.TOKEN_RENEW_TIMESTAMP`, and `"access_token_expiration"` is removed from any `UaaSecureStorage` shared-data list.

[discrete]
===== TokenConfiguration.generatedTokenExpirationHeaderName removed

The optional property `generatedTokenExpirationHeaderName` has been removed from the `TokenConfiguration` interface.

Note the changed behaviour: when the token lifetime is expired, the `LOGIN_REQUIRE` action is now dispatched. The server now provides `token_expiration_in_seconds` alongside the existing token response fields. The client uses this value to compute a `token_expiration_timestamp` and schedules a task that dispatches `LOGIN_REQUIRE` when the token lifetime expires.

*Required:* Yes, if your token configuration objects set `generatedTokenExpirationHeaderName`.

*Migration:* Manual.

*Result:* Usage of `generatedTokenExpirationHeaderName` is removed; the `access_token_expiration` response header is no longer read or stored, and token renewal is controlled exclusively via `token_renew_in_seconds`. When the token lifetime expires, the client dispatches `LOGIN_REQUIRE`.
